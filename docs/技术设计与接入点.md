# 技术设计与接入点

> 基线：DSH `dsh-v0.2.1-rc.2`（commit `687f282e`，源码检出 `E:\Project\Open_Source\deepseek-harness`）。核查日期 2026-10-20。
> 状态：源码级结论 + 合成图验证通过；运行实例激活与真实路由兼容性**未验证**。

## 一、接入点结论

`readImageRequest` 是唯一的模型请求图片投影入口，但没有格式/无损策略参数：

- `AttachmentStore` 是 cordis `Service` 子类，构造时注册服务名 `attachments`
  （`packages/attachment/attachment/src/index.ts:53-56`）；`readImageRequest` 默认直接拒绝
  （同文件 `249-261`）。
- `llm-pi-ai` 构建请求时统一调用它：`attachments.readImageRequest(ref, requestImageTarget(ref, budget), signal)`
  （`packages/llm/llm-pi-ai/src/context.ts:111-128`），随后按 `maxRequestImageBytes` 做
  `IMAGE_OFFLOAD_REQUIRED` 预检（同文件 `343-356`）。
- `ImageRequestTarget` 只有 `width/height/maxBytes`，没有格式字段。

**同名服务不能二次 provide**：cordis 在名字已被其他 fiber 注册时抛
`service "<name>" has been registered at <...>`（`vendor/cordis/src/reflect.ts:289-291`）；
`reflect.set()` 也只允许提供者自己的 fiber 覆写（同文件 `254-265`）。因此"包装现有实例"的
装饰器方案在纯插件层面不成立。

**可行方案**：本插件自己提供 `attachments` —— 子类化 `@deepseek-ai/dsh-attachment-local` 的
`LocalAttachmentStore`，只重写 `readImageRequest`；bundle patch 把 base 的 `attachment-local`
行 `disabled: true`，再插入自己的一行。

- 官方行：`packages/bundle/base/cordis.patch.yml:146-147`（`id: attachment-local`）。
- 可继承的构造与重写点：`packages/attachment/attachment-local/src/index.ts:147-175`、`248-254`。
- patch 方言支持按 id 覆盖既有行；跨 bundle 层后写入者胜出。

## 二、为什么不采用其他路线

| 路线 | 原因 |
| --- | --- |
| `tools/post-execute` 预压缩 | 只覆盖工具结果，覆盖不了用户上传与会话内既有图片 |
| `llm/stream` waterfall 改写 | 收到的是已注册引用，不含字节；改写历史消息违反请求冻结约束 |
| 直接覆写 `attachments` 实例方法 | 非 cordis 正式 seam，加载顺序敏感、无所有权、失败静默 |
| 复制一套 AttachmentStore | 承担存储、准入、校验、文件、GC 相关职责，超出单插件范围 |
| 只改规范化阶段 | 会改变持久附件身份与历史表示，违反"只处理请求版本" |

## 三、保真口径（口径 B）

原生请求路径的事实（`request-image.ts:103-118`、`encoding.ts:6-8`）：

- 目标尺寸 ≥ 源尺寸且源字节 ≤ 目标字节 → **原样透传**；
- 否则质量阶梯 `[85, 75, 60]`：透明图 → 有损 WebP（effort 0），不透明图 → JPEG。

因此"严格无损"必须以**请求栅格**为基准，而不是以路由最终发出的字节为基准：

1. 请求栅格 = 规范化附件 → sRGB → 长边缩放到目标尺寸（不放大），与官方流水线同构。
2. 无损候选必须逐像素等于该栅格（尺寸、通道、RGBA 字节全等），WebP 必须
   `lossless: true` **且** `exact: true`；PNG 只提高压缩级别，不启用量化。
3. 候选与**原生请求版本字节**比较：严格更小才采用，否则原样返回原生结果。

结果：

- 原生透传时，插件把 PNG/WebP 无损重编码，等价于"严格无损换更小编码"。
- 原生要走有损阶梯时，插件得到同尺寸、无损于该栅格、且比有损输出更小的表达；不比原生差，
  也不额外引入有损步骤。
- 缩放是路由的尺寸预算要求，插件不引入**额外**降采样。

## 四、数据流、身份与缓存

```
llm-pi-ai → ctx.attachments.readImageRequest(ref, target)
  → 官方实现生成 baseline（透传或质量阶梯）
  → 插件判据：启用？字节量？GIF/动图/深度/色彩空间/JPEG 来源？
  → 读缓存（<cache>/attachments/request-image-preprocess/<xx>/<hash>）
  → 未命中：重建请求栅格 → 编码候选 → 元数据 + 逐像素校验 → 取最小
  → 写入缓存并返回；无收益或失败 → 返回 baseline
```

- **身份**：`variantId = sha256({plugin, POLICY_VERSION, baseVariantId, candidates, effort})`。
  同一附件、目标、原生结果与策略恒定；策略或原生编码参数变化必然换身份。`POLICY_VERSION`
  在改动候选集合或编码参数时必须提升。
- **缓存**：落在官方附件缓存根下的独立目录，不写进持久附件树；内容寻址、原子写入（临时文件
  + rename）。缓存命中只做元数据探测，与官方 readCached 一致。
- **负缓存**：进程内记住"无收益"的原生身份（有界），避免每个请求重复付出编码代价。
- **并发**：插件自己的限流器（默认 2），不复用官方私有 limiter。

## 五、失败与回退

| 情况 | 行为 |
| --- | --- |
| 解码/编码/校验失败 | 返回 baseline，并记负缓存 |
| 缓存读失败或元数据不符 | 按未命中处理 |
| 缓存写失败 | 本次返回 baseline（不缓存），不影响该请求 |
| 调用方取消 | 抛出取消原因（与官方一致），不回退 |
| 服务构造失败 | 直接失败（fail-fast），不留半可用状态 |

## 六、与官方实现的耦合点（升级时必须复核）

1. `LocalAttachmentStore` 的构造签名 `(ctx, config)` 与继承的 `Config` 字段。
2. `readImageRequest` 的语义：透传条件、质量阶梯、`variantId` 派生、`RequestImageAttachment` 字段。
3. 请求栅格构造：`sharp(data, { failOn:'error', limitInputPixels:false }).toColourspace('srgb')`
   + 按 `ref` 长短边选择 `resize({ width | height, withoutEnlargement: true })`。
4. alpha 兼容规则（`encodedAlphaIsCompatible`）：WebP 可省略全不透明 alpha 平面。
5. 官方 `attachment-local` 行 id 与 `ctx.attachments` 服务名。
