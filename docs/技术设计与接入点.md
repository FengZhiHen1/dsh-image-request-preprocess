# 技术设计与接入点

> 基线：DSH `dsh-v0.2.1-rc.2`（commit `687f282e`，源码检出 `E:\Project\Open_Source\deepseek-harness`）。核查日期 2026-10-20，装饰方案改写 2026-10-21。
> 状态：源码级结论 + 离线合成图验证通过；运行实例激活与真实路由兼容性**未验证**（见 §七）。

## 一、接入点结论

`readImageRequest` 是唯一的模型请求图片投影入口，但没有格式/无损策略参数：

- `AttachmentStore` 是 cordis `Service` 子类，构造时注册服务名 `attachments`
  （`packages/attachment/attachment/src/index.ts:53-56`）；`readImageRequest` 默认直接拒绝
  （同文件 `249-261`）。
- `llm-pi-ai` 构建请求时统一调用它，且对一条请求里的**所有图片并发**调用：
  `Promise.all(orderedRefs.map(ref => attachments.readImageRequest(ref, requestImageTarget(ref, budget), signal)))`
  （`packages/llm/llm-pi-ai/src/context.ts:111-128`），随后按 `maxRequestImageBytes` 做
  `IMAGE_OFFLOAD_REQUIRED` 预检（同文件 `343-356`）。
- `ImageRequestTarget` 只有 `width/height/maxBytes`，没有格式字段。

**同名服务不能二次 provide**：cordis 在名字已被其他 fiber 注册时抛
`service "<name>" has been registered at <...>`（`vendor/cordis/src/reflect.ts:289-291`）；
`reflect.set()` 也只允许提供者自己的 fiber 覆写（同文件 `254-265`）。

### 采用：在官方实例上装饰，不接管服务

`ctx.attachments` 继续由官方 `attachment-local` 行提供；本插件声明 `inject: ['attachments']`，
在 `apply` 里把该实例的 `readImageRequest` 换成自己的包装，并用 `ctx.effect` 注册还原：

```
apply(ctx) → store = ctx.attachments
           → ctx.effect(() => { store.readImageRequest = decorator; return () => restore })
```

- 本 bundle 的 patch **只插入自己的一行**，不禁用、不改写任何官方行。
- 提供者缺席或没有 `readImageRequest` ⇒ 不激活、只 warn：**失败即不优化**，附件功能照常。
- `attachments` 换实现时 cordis 重新执行 `apply`（`inject` 是声明式依赖），旧装饰随 fiber 卸载还原。
- 装饰标记用 `Symbol.for`，重复 `apply` 不会把包装层叠起来。

### 为什么放弃"接管服务"（曾经的 v0.1.0 方案）

v0.1.0 子类化 `LocalAttachmentStore` 自己 provide `attachments`，patch 用
`- id: attachment-local / disabled: true` + `insert`。它在 test 实例上让宿主进程两次在本轮内退出，
见 §七「事故记录」。除了事故本身，这个方案的爆炸半径也明显更差：

| | 接管服务（v0.1.0） | 装饰实例（v0.1.1） |
| --- | --- | --- |
| 本行禁用官方行 | 是，`ctx.attachments` 的提供者在启停本 bundle 时被拆掉重建 | 否 |
| 本行失败/不兼容 | `ctx.attachments` 缺失，图片与会话图片读回全部受影响 | 不优化，其余照常 |
| 依赖官方运行时包 | 需要 `@deepseek-ai/dsh-attachment-local`（`link:` 安装下解析到自己的副本，含另一份 cordis/Service） | 不 import 任何服务类 |
| 与官方实现耦合面 | 构造签名、Config 字段、全部继承方法与内部字段 | `readImageRequest` + `readImage` 两个方法 |

代价：装饰是"改别人的实例方法"，不是 DSH 文档化的 seam。它换来的是可撤销（`ctx.effect`）
与失败面收敛。这是本插件唯一接受的越界，判据写在 `plugins/AGENTS.md` 之外的本篇与 README
「已知边界」里。

### 其他不采用的路线

| 路线 | 原因 |
| --- | --- |
| 接管整个 `attachments` 服务 | 见上：爆炸半径 + 实例事故 |
| `tools/post-execute` 预压缩 | 只覆盖工具结果，覆盖不了用户上传与会话内既有图片 |
| `llm/stream` waterfall 改写 | 收到的是已注册引用，不含字节；改写历史消息违反请求冻结约束 |
| 复制一套 AttachmentStore | 承担存储、准入、校验、文件、GC 相关职责，超出单插件范围 |
| 只改规范化阶段 | 会改变持久附件身份与历史表示，违反"只处理请求版本" |

## 二、保真口径（口径 B）

原生请求路径的事实（`request-image.ts:103-118`、`encoding.ts:6-8`）：

- 目标尺寸 ≥ 源尺寸且源字节 ≤ 目标字节 → **原样透传**；
- 否则质量阶梯 `[85, 75, 60]`：透明图 → 有损 WebP（effort 0），不透明图 → JPEG。

因此"严格无损"必须以**请求栅格**为基准，而不是以路由最终发出的字节为基准：

1. 请求栅格 = 规范化附件 → sRGB → 长边缩放到目标尺寸（不放大），与官方流水线同构。
2. 无损候选必须逐像素等于该栅格（尺寸、通道、RGBA 字节全等），WebP 必须
   `lossless: true` **且** `exact: true`；PNG 只提高压缩级别，不启用量化。
3. 候选与**原生请求版本字节**比较：严格更小才采用，否则原样返回原生结果。

## 三、请求路径的成本护栏

装饰点位于模型请求的关键路径上（每条请求的所有图片并发进入），所以"会不会拖住请求"是设计
的一部分，不只是性能问题：

| 护栏 | 做法 | 依据 |
| --- | --- | --- |
| 单图时间预算 | `AbortSignal.timeout(budgetMs)` 与调用方信号合并，`Promise.race` 里**不依赖被调用方配合**地放弃等待 | 原生解码/编码不接受取消，只靠 `throwIfAborted()` 无法打断卡住的原生调用 |
| 并发上限 | 插件自己的单槽 FIFO（默认 1），排队也响应中止；**槽位在中止时立刻归还** | 一次永不返回的原生调用不能把后续请求排队到死 |
| 只校验可能入选的候选 | 候选字节 ≥ "原生与已通过候选"的最小者时直接跳过解码校验 | 它已经在 `chooseSmallest` 里注定落选 |
| 零拷贝比对 | `Buffer.from(data.buffer, byteOffset, byteLength)` 视图 | 4 MP 栅格 16 MiB，复制一次就是一份无谓的垃圾 |
| 失败记账 | 无收益、失败、超预算都记进有界负缓存 | 避免每个请求为同一张图重复付出编码代价 |

实测（合成 2048×2048 截图样图，本机 Windows / sharp 0.35.5）：渲染请求栅格 13 ms、
WebP Lossless effort 4 约 110 ms、effort 2 约 100 ms（首次含预热）、优化 PNG level 9 约 42 ms、
解码校验 53 ms、原始请求栅格 16 MiB。**结论：单图成本在 100 ms 量级，不是秒级**，所以
"编码太慢拖死宿主"不成立；默认仍取 `effort: 2` / `concurrency: 1` / `budgetMs: 2500` 留足余量。

## 四、数据流、身份与缓存

```
llm-pi-ai → ctx.attachments.readImageRequest → 装饰层
  → 官方 readImageRequest 生成 baseline（透传或质量阶梯）
  → 判据：启用？字节量？GIF/动图/深度/色彩空间/JPEG 来源？
  → 读缓存（<cache>/attachments/request-image-preprocess/<xx>/<hash>）
  → 未命中：预算内（排队 + 读源 + 重建请求栅格 + 编码候选 + 校验 + 取最小 + 写缓存）
  → 有收益则返回派生版本；无收益/失败/超预算 → 返回 baseline
```

- **身份**：`variantId = sha256({plugin, POLICY_VERSION, baseVariantId, candidates, effort})`。
  `POLICY_VERSION` 在改动候选集合或编码参数时必须提升（当前 `v2`：默认 effort 与候选校验
  路径变更，旧缓存不复用）。
- **缓存**：`<cache>/attachments/request-image-preprocess/`，内容寻址、原子写入（临时文件 + rename），
  不写进持久附件树。缓存根由 `dshCachePath('attachments')` 解析（与官方 `cacheRoot` 同源，
  除非实例显式给 `attachment-local` 配了 `dshHome`——只影响缓存位置，不影响正确性）。
- **负缓存**：进程内记住"无收益/失败/超预算"的原生身份（有界 2048）。

## 五、失败与回退

| 情况 | 行为 |
| --- | --- |
| 解码/编码/校验失败 | 返回 baseline，并记负缓存 |
| 超出 `budgetMs` | 停止等待（原生调用可能仍在跑），返回 baseline，并记负缓存 |
| 缓存读失败或元数据不符 | 按未命中处理 |
| 缓存写失败 | 本次返回 baseline（不缓存），不影响该请求 |
| 调用方取消 | 抛出取消原因（与官方一致），不回退 |
| 提供者没有 `readImageRequest` | 本插件不激活，只记 warn |
| 装饰/还原异常 | `ctx.effect` 负责还原；异常不进入请求路径 |

## 六、与官方实现的耦合点（升级时必须复核）

1. `ctx.attachments` 上有 `readImageRequest(ref, target, signal)`，语义：透传条件、质量阶梯、
   `variantId` 派生、`RequestImageAttachment` 字段。
2. `ctx.attachments.readImage(ref, signal)` 能读回已校验的规范化附件字节。
3. 请求栅格构造：`sharp(data, { failOn:'error', limitInputPixels:false }).toColourspace('srgb')`
   + 按 `ref` 长短边选择 `resize({ width | height, withoutEnlargement: true })`。
4. alpha 兼容规则（`encodedAlphaIsCompatible`）：WebP 可省略全不透明 alpha 平面。
5. `ctx.attachments` 服务名与 `attachment-local` 行 id。
6. 服务实例可被赋值覆盖方法（本装饰的前提）：cordis 的非 callable `Service` 构造后返回自身实例，
   `ctx.reflect` 取值时按实例/原型查找，因此实例上的自有属性对通过 `ctx.attachments` 的调用可见。
   若某版本把服务实例冻结或改为代理，本插件会退化成"不生效"（包装未挂上），不会伪造成功。
